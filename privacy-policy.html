This policy is intended for the OPTIMUS extension release configured to use the API at https://optimus-eewm.onrender.com. A different extension build may send information to a different API. Check the extension’s data notice and the API address in the installed release.

What OPTIMUS does

OPTIMUS classifies a submitted web address as phishing or legitimate and displays the model’s confidence estimate. The service processes the URL text; the extension’s prediction request does not ask the destination website to provide its page contents.

When a URL is sent

The extension asks for affirmative consent before scanning. After you enable scanning, it automatically sends the full URL for qualifying HTTP or HTTPS page navigations to the API. The URL can include the domain, path, query parameters, and fragment. These parts can contain personal information, search terms, account identifiers, or secret values. Do not scan a private page or a URL containing credentials or other information you do not want sent to the service.

Automatic scanning excludes the following hostnames and their subdomains: google.com, google.co.in, bing.com, yahoo.com, duckduckgo.com, ecosia.org, search.brave.com, yandex.com, and baidu.com. A manual scan from the popup sends the HTTP or HTTPS URL shown or entered there; the automatic-scan exclusion list does not restrict that manual scan.

The extension also contacts the configured API’s health endpoint to show whether the service and model are available. It sends prediction requests to /predict and feedback requests to /feedback.

Information the service stores

When a prediction succeeds, the application stores the submitted URL, prediction time, predicted class, confidence score, and model version in a SQLite database. A URL may reveal sensitive information even when the website itself is public.

If you submit feedback, the application stores the label you selected and its timestamp with the prediction. It also records feedback and review history, including the label claim, review status, reviewer and provenance information when a review occurs, and any recorded reason. Submitting feedback is only a user claim: it does not by itself verify the label or make the record eligible for training. A reviewer must separately verify it before it can be considered for a training batch.

The application code does not define collection of account profiles or payment details. The hosting platform or network infrastructure may process technical request information, such as information needed to deliver and operate the service; the exact logs and fields retained by the live deployment have not been confirmed.

Why information is used

URLs are used to return a phishing-detection result. Feedback may be reviewed to assess the reported label. Only separately reviewed, verified, provenance-bearing feedback can become eligible for a training batch under the project’s safeguards. A user report is not automatically used to train or replace the active model.

Where information goes and who may access it

The extension sends requests to the API origin configured in that extension build. For the release described here, the configured origin is the Render-hosted address shown above. The API service and its hosting infrastructure process these requests to provide the service. The project code does not show analytics or advertising integrations or another URL-sharing destination.

The application stores prediction and feedback records in SQLite. People with access to the service’s database or hosting environment may be able to access those records. Authorized reviewers may inspect URLs associated with feedback when reviewing a label. The prediction and feedback API routes do not require a user account. The separate prediction-history route is disabled unless an operator configures a shared access token; when enabled, it omits URLs by default but can return them when an authorized caller explicitly requests them.

The application does not encrypt its SQLite database itself. Whether the current hosting storage is encrypted at rest, who at the hosting provider can access service data, what request and application logs are retained, and whether backups contain these records have not been confirmed. This policy does not make a promise about those unverified controls.

Retention and deletion

The application has no automatic retention period or user-facing deletion feature. Disabling scanning stops future extension requests from that browser profile, but does not delete records already stored by the service. The project does not currently define a supported process or timeframe for handling an individual deletion request. Records may therefore remain in the database unless the service operator removes them; the handling of backups and hosting logs is also unconfirmed.

Your choice

You can decline consent or disable scanning in the extension popup. Revoking consent removes the extension’s saved consent setting and prevents later automatic scans, manual scans, and feedback requests from that browser profile until consent is given again. It does not recall a request already sent or erase server-side records.

Model results

A prediction and its confidence are model estimates, not guarantees. Do not rely on OPTIMUS as the only basis for deciding whether a website is safe.
